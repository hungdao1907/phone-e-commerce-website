## 2. Quotation API and checkout activation

`createQuotationRouters()` returns three routers intended for:

- customer: `/api/quotations` (create/recovery, own list/detail, confirm/decline, private PDF);
- assigned Staff: `/api/staff/quotations` (assigned list/detail, approve/reject, private PDF);
- Admin/Superadmin: `/api/admin/quotations` (assignment/management and authorized PDF access).

The factory receives the Prisma-compatible database, backend pricing provider, order converter, expiry policy and private-storage roots. Its handlers use authenticated roles and customer ownership/staff assignment checks; mock tests cover those policies. It is not composed in `backend/src/index.ts`. Mounting must wire all dependencies deliberately and run the authorization suite against the composed app. The Customer frontend flag does not protect a mounted backend route from direct HTTP calls. If a dark-mount/kill switch is required, add a backend-side gate before activation; otherwise treat router mount as the public activation boundary.

The API source relies on Quotation/Idempotency schema and generated Prisma types. `prisma validate` does not generate the client. Generate only after an approved, reconciled migration plan and with the exact release schema/client versions.

Direct Checkout is authenticated Customer-only; guest checkout is not the current `/api/orders` contract. When Checkout idempotency is enabled, the backend requires a valid `Idempotency-Key`; when disabled, a request carrying that header returns `503 IDEMPOTENCY_NOT_ACTIVATED`. The frontend flag is compile-time and the client persists a retry intent without PII. Therefore:

1. keep both flags off until the Checkout table exists and the deployed client is generated;
2. enable backend and frontend in the same coordinated release/window (or implement and test a backwards-compatible staged contract first);
3. verify same-key/same-payload returns the original Order, changed payload conflicts, and replay does not reserve stock/promo or emit success notifications twice.

Order creation, payment writes, stock reservation and promo reservation are in a transaction in source. Quotation conversion has a unique quotation link and transactional state transitions. Mock tests pass, but actual PostgreSQL isolation, unique-index collision behavior and deadlock/serialization retry are **DB_CONCURRENCY_NOT_VERIFIED**.

## 4. Private PDF, notifications and other security gates

**PDF:** Express static middleware denies any decoded path segment named `quotations`; malformed or deeply encoded paths fail closed. Private storage rejects roots overlapping public uploads, uses random keys and verifies SHA-256/size/path at download. Customer ownership, assigned Staff, Admin role and `private, no-store` headers are covered by mock/isolated tests. Thirteen old PDFs remain in `backend/uploads/quotations`; none was deleted or moved. The reverse proxy/CDN/web-server configuration is absent from this repository review. Before opening quotation downloads, configure and externally verify that direct legacy URLs and static aliases return denied/not found, while product/banner images remain public.

**Notifications:** the quotation event envelope is only a contract; no durable outbox/worker/email integration exists. Existing Direct Checkout email and DB notification dispatch occurs after commit and is best-effort, so a crash can lose a notification; this is not exactly-once. The current event contract lacks an explicit `quotation.customer_confirmed` event. Minimum events for product policy are: quote created/confirmation required, Customer confirmed, Admin assigned Staff, Staff approved/rejected, NEEDS_REQUOTE, and Order created. If best-effort post-commit dispatch is accepted for first activation, document that loss risk and add monitoring/reconciliation. If durable notification is required, add a transactional outbox (unique dedupe key, event payload/version, status/attempt/lease timestamps, error metadata), write it in the same business transaction, and deploy a retrying worker with provider idempotency where available. Do not claim exactly-once email delivery.

Security classification:

- **CRITICAL_BLOCKER:** migration history/empty migration cannot be reconciled from source; private PDF proxy/static boundary is unverified; active MAIN still contains a legacy PDF upload path that currently receives HTTP 410 and its public-trigger/network boundary is not verified; free-text PII handling and provider retention need an owner decision before new AI data flow.
- **REQUIRED_BEFORE_ACTIVATION:** reviewed migration sequence and backup/restore proof; correct Prisma Client; backend router composition/authorization smoke; private-root/proxy proof; synchronized Checkout flags; freeze a deployable artifact containing the currently untracked draft SQL/source; user-directed E2E after Chatbot completion before widening traffic.
- **ACCEPTED_LIMITATION (single process only):** Quotation create limiter and order-tracking OTP challenges/proofs/rate buckets are in-memory. Process restart clears them; multiple replicas do not share them. `trust proxy` is not configured, so behind a proxy `req.ip` can collapse to the proxy peer. Configure only known proxy hops/networks (never trust arbitrary `X-Forwarded-For`) or use a shared edge/store before scaling.
- **POST_RELEASE_IMPROVEMENT:** distributed rate limiting/OTP state, durable notification outbox if best-effort loss is accepted, and operational dashboards/alerts.

DELETE review relevant to preserving Staff scope: Product deletion checks protected history/dependents transactionally; Category uses the safe deletion service; Customer deletion rejects protected transaction history; Lead deletion scopes ownership and blocks interaction history; Promo checks existing Orders transactionally and restrictive quote FK applies only once migrated. Banner has authenticated Staff/Admin `DELETE /` and `/all` handlers that call `deleteMany({})` with no server-side confirmation token; treat as a configuration-availability risk (UI confirmation is not an API security boundary). Campaign/Footer/Reward deletion can remove configuration/linked rows according to current FK behavior; keep backups and review FK state. These are not Quotation schema blockers, but broad Banner deletion remains a deliberate Staff capability risk.
